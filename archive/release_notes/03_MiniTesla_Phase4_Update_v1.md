# MiniTesla 第四階段：影像斷線處理與恢復接管

本包接續已安裝的第一、二階段及第三階段。只包含本次新增或修改的 6 個完整程式檔，以及本說明，共 7 個檔案。請合併覆蓋，不要刪掉原資料夾。

## 本次完成

- 手動接管前，必須收到電腦端對新影格的接收確認。
- 影像接收器完整收到 JPEG、成功解碼並交給顯示流程後，才回覆該影格編號。
- 影像斷線、確認逾時、影格過期或傳送程序停止時，手動模式轉成故障待命，輸出中立。
- 即使控制通訊仍正常，影像失聯也會停止。
- 影像傳送會自動重連，電腦接收器也會重新等待連線；重連不會自動恢復油門。
- 電腦控制視窗及 Jetson 狀態監看，新增影像是否就緒、影格年齡與失聯原因。
- 電腦端目標 IP 統一使用 `120.126.10.41`。

本階段是手動遙控的失聯處理。巡邏、人物警示、自動避障決策與停車仍待後續加入；目前沒有失聯後自動巡邏或自主續駛。

## 一、替換檔案

先停止兩端正在執行的舊程式。雷達 SDK、本來的模型與 Python 環境繼續使用。

| 壓縮包內檔案 | 操作 |
| --- | --- |
| `Jetson/minitesla.py` | 覆蓋車端同名主程式 |
| `Jetson/minitesla_sensors/control.py` | 覆蓋原感測模組資料夾內同名檔 |
| `Jetson/minitesla_sensors/io.py` | 覆蓋原感測模組資料夾內同名檔 |
| `Jetson/sensor_status.py` | 覆蓋車端同名監看程式 |
| `PC/pc_control.py` | 覆蓋電腦端第三階段控制程式 |
| `PC/pc_receive.py` | 新增電腦端接收程式，以它取代舊 `from_jetson_orin_nano(1).py` |
| `README_使用說明.md` | 本說明 |

Jetson 的 `minitesla_sensors` 資料夾仍應有 `__init__.py`、`core.py`、`io.py`、`control.py` 四個檔案。其中 `__init__.py` 與 `core.py` 本次沒改，所以沒有重複附上。原 `sensor_config.json`、`best.pt`、`rplidar_sdk-master` 保留。

M4 韌體與接線本次未改，不需重新燒錄。不需下載新驅動或安裝新的 Python 第三方套件：電腦端沿用原 OpenCV、NumPy，控制視窗沿用 Tkinter。

**兩端影像協定都必須更新。**舊影像接收器沒有影格確認功能，因此不能再拿來搭配本版主程式。請關閉舊 `from_jetson_orin_nano(1).py`，以免占用相同連接埠。舊 `sever(1).py`、Jetson 舊 `lidar_receive.py`、`detect.py`、`jetson_motor_uart_verbose.py` 也不要和正式主程式一起啟動。

## 二、啟動電腦端

將 `pc_control.py` 與 `pc_receive.py` 放在電腦端程式資料夾。在同一資料夾開兩個終端機，分別執行：

```powershell
py pc_receive.py
```

```powershell
py pc_control.py
```

如果你原本使用 `python` 指令，將 `py` 換成 `python`，並使用原本已安裝 OpenCV、NumPy 的環境。控制視窗會顯示第 4 階段；影像視窗收到第一張影像後才會出現。

連接埠保持原配置：控制使用 UDP 5000，雷達使用 UDP 6000，影像使用 TCP 7000。影格確認走同一條影像 TCP 連線，不需要新增連接埠或重新設計 MiFi／5G／NAT 穿透。若防火牆對新程式出現提示，允許它在原本使用的網路接收通訊。

## 三、啟動 Jetson

以下沿用你截圖中的資料夾名稱，假設整個 `jetson orin nano` 放在 Jetson 桌面。

第一個終端機：啟動原雷達 SDK 讀取程式。

```bash
cd "$HOME/Desktop/jetson orin nano/rplidar_sdk-master/output/Linux/Release"
./ultra_simple --channel --serial /dev/ttyUSB0 460800
```

第二個終端機：啟用原本的模型推論環境，再執行主程式。

```bash
cd "$HOME/Desktop/jetson orin nano"
python3 minitesla.py --pc-host 120.126.10.41
```

第三個終端機為選用的狀態監看：

```bash
cd "$HOME/Desktop/jetson orin nano"
python3 sensor_status.py
```

沒有 Jetson 本地桌面時，主程式指令加 `--no-display`。模型仍使用既有 `best.pt`。

主程式內建預設目標 IP 已改為 `120.126.10.41`。保留的設定檔若原本有填其他 IP，仍會尊重該設定；上面統一使用 `--pc-host 120.126.10.41`，可直接覆寫設定檔。日後你只要改這個參數，或修改 `sensor_config.json` 的 `network.pc_host`。

## 四、正常操作與斷線恢復

1. 等影像出現，控制視窗顯示「影像：接收確認正常」，四向 ToF 與 M4 也必須就緒。
2. 點選控制視窗，按 `M`；等顯示「手動就緒」再使用 `W/S/A/D`。
3. 按空白鍵停止並回待命。控制視窗失去焦點也會要求停止。
4. 如果影像失聯，車端進入故障待命。接收程式仍在執行時會自動等待重連；若已關閉或崩潰，重新啟動 `pc_receive.py`。
5. 畫面恢復且顯示影像確認正常後，回到控制視窗按 `R` 解除故障，再按 `M` 接管。必須重新按下方向鍵；斷線前按住的油門不會自動恢復。

| 狀態 | 處理方式 |
| --- | --- |
| 尚未收到影格確認 | 確認新版 `pc_receive.py` 已啟動，等待相機及模型載入完成 |
| 影像連線中斷 | 檢查原網路／接收程式，等待自動重連，再 `R` → `M` |
| 影格確認逾時 | 對方沒有在期限內確認影像；恢復影像後再 `R` → `M` |
| 影格已過期 | 檢查攝影機、推論及網路是否停滯；不能用舊影格取得控制權 |
| 影像傳送程序已停止 | 檢查 Jetson 終端機訊息，重新啟動車端主程式 |
| M4／ToF 保護原因 | 沿用上一版處理方式，影像恢復不能繞過底層保護 |

影像或雷達視窗按 `Q`／`Esc`、關閉視窗，或接收程式按 `Ctrl+C`，會結束這組影像／雷達接收程序。此時手動行駛也會因影像失聯而停止。停止正式車端主程式時使用 `Ctrl+C`。

## 五、時序及相容性

手動控制心跳逾時仍為 300 毫秒。影格有效期限預設 1 秒，從 Jetson 擷取前開始計算，包含擷取、推論、佇列等待、網路傳輸與確認回程。只建立 TCP 連線、只成功寫入本機傳送緩衝區，或延遲收到過期確認，都不算影像就緒。

所有模式故障都由原單一串列輸出流程送中立，M4 原保護仍有最高優先權。上述秒數是軟體判斷門檻，不等於保證實體車輛在相同時間內完全停止。

影像改用長度有上限的原始 JPEG 封包與影格序號，最多 8 MiB／影格；不再使用原先的 Python 物件序列化影像封包。每張影格確認後才送下一張，壅塞時取最新影格，因此顯示幀率會受網路往返延遲影響。本次沒有更改模型、JPEG 品質設定或 M4 控制頻率。

若未修改設定檔，本包的控制預設值已足夠載入，不必新增設定欄位。程式保留 `control.video_timeout_s` 可設 0.2～2.0 秒，預設為 1.0；本包沒有替你改動原設定檔。

## 六、已做的軟體驗證

通過 68 項測試，包含原本模式切換與電腦操作的回歸測試、真實本機 TCP／UDP 插孔、模擬 UART，以及：

- 尚未取得影格確認時禁止接管。
- 控制 UDP 仍有資料、影像中斷時，串列輸出改成中立。
- 半包、拆包、錯誤長度、錯誤確認序號、過期影格與無回覆均不誤判成功。
- 斷線重連、恢復後禁止自動起步、必須重新解除故障並接管。
- 有界事件佇列即使漏掉單筆斷線通知，後續累積斷線數仍會保留失聯證據。

另已確認 Python 3.8 語法及與上一版保留檔案合併後的載入。此處未連接你的實車，沒有執行 Jetson GPU 推論或 Windows 圖形介面；新增功能的實車行為仍待你部署後確認。
